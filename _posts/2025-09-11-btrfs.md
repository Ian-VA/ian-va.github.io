I have been running and using the BTRFS filesystem for around a decade now, with very few complaints. It's good at what it does, works out of the box, and I find myself having to do very little "maintenance" on my system. However, when it fails, it fails so terribly that your solution is probably "wipe your drive and start over". This is what (almost) happened to me, and this post is dedicated to how I fixed it.

---

## Conventional Disk Cloning Methods

Recently, I built a new system for myself and had to clone my BTRFS filesystem from a 500GB SATA SSD drive to a 4TB NVMe SSD. There are a couple of solutions for doing this, and the popular ones are generally:

* Use [Clonezilla](https://clonezilla.org/) on a live USB/hard drive and attach both the source and target disks to the system, then boot to Clonezilla, select the option to put it on RAM, and clone your disk
* Create partitions with (g)parted and use dd like so:
   ```bash
   sudo dd if=/dev/source_disk of=/dev/target_disk bs=32M status=progress
   ```

I wanted to use Clonezilla, so I opted for a process like this:

* Burn a Clonezilla ISO on a USB hard drive
* Put Clonezilla on RAM, then connect old SATA SSD disk to new system with NVMe SSD
* Clone the disk by following Clonezilla's GUI

However, booting into a cloned disk after Clonezilla successfully finished revealed this mess:

```
[    9.480593] BTRFS error (device nvme0n1p1): bad tree block start, mirror 1 want 84869120 have 0
[    9.480717] BTRFS error (device nvme0n1p1): bad tree block start, mirror 2 want 84869120 have 0
```

Apparently, Clonezilla has a lot of trouble with BTRFS filesystems. These BTRFS errors were uncorrected with a ```btrfs scrub```, and while my filesystem could mount, it seemed to have corrupted enough data to be essentially unusable. Mainly, I got repeated I/O errors in my ```.cache``` directory. These errors weren't traceable to a set of corrupted files with ```dmesg``` either, meaning it was most likely corrupted metadata. Here's what I did to fix it.

--- 

## Preparing the new drive

If your new disk is an NVMe SSD (like mine), wipe it quickly and securely by installing nvme-cli in a package manager and formatting it like so:

```bash
sudo pacman -S nvme-cli
sudo nvme format -s1 /dev/mynewdisk
```

Then, partition the disk to prepare it for your BTRFS filesystem:

```bash
sudo parted /dev/mynewdisk
(parted) mklabel gpt
(parted) mkpart primary btrfs 4MiB 100%
(parted) quit
```

This creates a primary btrfs partition on your disk. If you intend to boot with this disk, you'll also have to create a separate EFI FAT32 boot partition.

---

## Using BTRFS commands to clone a disk

From here, we have a couple options that I was previously ignorant to as a casual user of BTRFS. Some context:

* BTRFS is different from other conventional filesystems because it has built-in disk and volume management
* We can use this functionality to move data from one disk to another with already-available BTRFS commands

#### BTRFS replace

**Have backups before attempting this.**

The command that is built for moving BTRFS data from one disk to another is ```btrfs replace```. You can use it like so:

```bash
btrfs replace start /dev/myolddiskpartition /dev/mynewdiskpartition <mount-point>
```

Then resize the filesystem to cover the size of the new disk:

```bash
btrfs filesystem resize 1:max <mount-point>
```

In my case, running this in TTY, my mount point was simply ```/```. Do note that btrfs replace removes the source device from the filesystem, making it unusable for BTRFS.

#### BTRFS device add/remove

You can also achieve the same functionality by doing a ```btrfs device add``` followed by a ```btrfs device remove```, which forces the BTRFS filesystem to migrate all of your data to the disk you added (assuming you have only two disks in the filesystem after the add). This is done like so:

```bash
btrfs device add /dev/mynewdiskpartition <mount-point>
btrfs device remove /dev/myolddiskpartition
```

If you want the old disk to be kept around by the BTRFS filesystem, however, you can add it as a device and spread the data to it without removing it like so:

```bash
btrfs device add /dev/mynewdiskpartition <mount-point>
btrfs balance start -dusage=5
```

After doing any of these command sequences, your data should now be present on your new disk!

## Booting 

Now, if you're like me and you're keeping the old disk around for its boot partition, to make the system bootable to the new disk, find the UUID of your new disk:

```bash
sudo blikd /dev/mynewdisk
```

You should see something like this:

```bash
/dev/sdb: UUID="12345678-ABCD-90EF-1234-567890ABCDEF" TYPE="btrfs"
```

Take that UUID and drop it in the ```root=UUID=(old-uid)``` line in your bootloader entry in ```/boot/loader/entries/<your-entry>.conf```. Then, do a ```sudo bootctl update```. Check if this UUID is present in your ```/etc/fstab```, and if it is, your system is now bootable to your new disk!

Congratulations, you made it! I made this post so other unfortunate BTRFS users wouldn't have to dig through endless piles of documentation like me, and tried to make it clear up a lot of the information I found lacking in other guides. Have a good time using your new disk with BTRFS, and run a ```btrfs scrub``` weekly for maintenance.
